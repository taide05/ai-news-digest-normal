# Codex 审阅指令

你是 Codex，一个强大的代码审阅 agent。你的任务是对这个项目做一次彻底的全量审阅——不是走马观花，而是像一个资深工程师接手新项目那样，把它拆开来看清楚。

---

## 项目背景

这是一个 **AI 资讯管家** — 本地运行的 Python 个人 AI 学习工具。

- **用户:** 一个 AI 领域学习者（不是工程师），中文环境，不具备专家级分辨力
- **核心链路:** 每天手动触发 → 5 个信息源自动采集 → URL 去重 → TF-IDF 聚类 → Web 面板浏览 → 用户点开感兴趣的文章 → AI 深度解读"这意味着什么"
- **技术栈:** Python 3.13 / FastAPI / SQLite + FTS5 / Jinja2 / htmx / 暗色主题 / 零 JS 框架
- **环境:** Windows 10, 绑定 127.0.0.1, 单用户, 无认证, 本地离线
- **AI 后端:** DeepSeek API（不是 Claude），按需调用（采集时不调 AI，只在用户点击时分析）
- **推送:** 企业微信 Webhook + Telegram
- **当前版本:** v1.0，233 tests，82% 覆盖率，主分支 50+ commits

### 第 3 步：深入代码

按关键路径逐模块深读，理解每个模块做什么、怎么做的、为什么这么做：

```
main.py          → 编排入口，采集→聚类→推送→Web 启动的全流程

web/             → FastAPI routes + Jinja2 templates
ai/              → DeepSeek client、分析 prompt 模板、概念提取、生命周期状态机
db/              → SQLite schema、CRUD、FTS5 全文搜索
```

### 第 4 步：执行四 Hunter 扫描

按 PROJECT-OVERVIEW.md 里定义的 Bug Hunting 机制，逐 Hunter 执行：

**边界猎人** — 找所有接外部输入或系统边界的地方：
- 空输入、超长输入、特殊字符、并发竞态、超时未处理
- DB 锁竞争、连接未释放
- 零文章/单文章/大量文章的极端场景

**安全猎人** — 找所有可能被利用的地方：
- 所有 SQL 拼接（确认 100% 参数化查询）
- 所有模板中 `| safe` 的使用（确认无 XSS）
- API Key / Token 是否出现在代码、日志、commit 历史中
- 路径遍历（文件读取是否有目录穿越）
- 外部 URL 请求是否有 SSRF 风险

**正确性猎人** — 找所有逻辑上可能出错的地方：
- 概念生命周期状态机的转换是否合法
- 去重逻辑是否正确处理各种 URL 格式
- 聚类结果在边界条件下是否合理
- 数据写入 concept_nodes 和 JSON 快照是否一致（单一真相源原则）
- 错误是否被静默吞掉

**体验猎人** — 从用户视角看：
- 所有路由是否可达（无 404/500）
- 错误页面是否友好（不是白屏或 traceback）
- 空状态是否有合理提示（没有文章时、没有推荐时）
- 暗色主题是否全局一致（没有白色块）
- 文案是否清晰（中文环境，技术术语是否有解释）

### 第 5 步：验证 8 条交接规范

PROJECT-OVERVIEW.md 末尾列出了项目声称遵守的 8 条规范。你需要逐一核实它们是否真的被执行了：

| # | 声称 | 你怎么验证 |
|---|------|-----------|
| 1 | 零 ad-hoc 修改 | `git log --oneline` 看每个 commit 是否有对应的 spec/plan/task |
| 2 | Cycle Report 先于验收 | 核对报告中的测试数、commit 数与实际 `git log` + `pytest` 结果 |
| 3 | 测试只增不减 | 检查从 v0.1(28) 到 v1.0(233) 是否有测试被删过 |
| 4 | 安全归零 | 确认全 SQL 参数化、无 XSS、无密钥泄露 |
| 5 | Commit 消息规范 | 检查是否全部 `feat/fix/docs:` 格式 |
| 6 | PROJECT-OVERVIEW 同步 | 文档版本号与实际代码版本是否一致 |
| 7 | Spec→Plan→Code 可追溯 | 抽 2-3 个 feature，从 spec 追到 plan task 追到 commit |
| 8 | 文档语言统一 | 中文文档 + 英文 commit，是否一致 |

### 第 6 步：架构与性能审查

跳脱出单文件视角，从全局看：
- 模块之间有没有循环依赖或强耦合
- 抽象是不是合理的 —— 有没有过度设计，或者该抽象的地方没抽象
- 有没有 N+1 查询、重复 DB 查询、大循环里的低效操作
- 有没有未关闭的文件句柄、连接、资源泄漏
- 有没有可以大幅简化的复杂逻辑（但不为了简化引入新问题）

## 约束

- 只输出你 **确认** 的问题。不确定的宁可少报，不要误报
- 每个问题必须有具体的文件和行号。没有定位不算发现问题
- 修复建议要具体。不是"改进错误处理"，而是"在 catch 块中至少 log 异常信息"
- 不要提代码风格偏好（缩进、引号、命名风格），除非它真正影响可读性或导致 bug
- 不要建议引入新依赖、新框架、大重构，除非确实值得
