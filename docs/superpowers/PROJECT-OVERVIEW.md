**最后更新:** 2026-06-11

---

## 一、项目定位

一个本地运行的个人 AI 资讯学习工具。不是资讯推送器，是 **AI 学习导师**——帮用户把表层信息转化为可理解的深度知识。

**用户:** 一个人使用，AI 领域学习者，中文环境，不具备专家级分辨力，需要 AI 辅助理解"这意味着什么"。

---

## 二、终局愿景（v1.0+）

```
用户每天双击快捷方式
  → 自动采集 → 智能聚类 → 企微通知
  → Web 面板阅读 → AI 逐篇深度解读
  → 系统学习用户兴趣 → 个性化推荐
  → 周报/月报总结学习轨迹
```

## 五、标准开发循环（强制流程，不可跳过任何阶段）

**每个版本严格走完 A → B → C → D → T → E → F，T 是强制门禁，F 是收尾归档。**

```
阶段 A: 验收上一版本 ──── 确认上一版功能正常，发现回归bug
    │
    ▼
阶段 B: 代码审计 ──────── 架构+安全+质量+性能审查，修问题
    │
    ▼
阶段 C: 需求规划 ──────── brainstorming + 多视角审查(aesthetic/systems/logic) → spec → plan
    │
    ▼
阶段 D: 开发 ──────────── subagent-driven，逐task实现+审查，TDD
    │
    ▼
阶段 T: 系统测试 🔴门禁── 全量/回归/边界/集成/性能/安全/覆盖率
    │                    任何失败 = 回到 D 修复，T 不过不能进 E
    ▼
阶段 E: 验收 ──────────── 验证所有 v0.x 行为，确认可交付
    │
    ▼
阶段 F: 归档准备 ──────── Cycle Report + PROJECT-OVERVIEW 同步 + 规则审计 + 下一版本种子
```

### 阶段 F: 归档与规则审计

**每个版本完成后的收尾阶段。确保所有决策和规则落地为文档。**

1. **Cycle Report** — 写入 `docs/superpowers/reports/YYYY-MM-DD-cycle-N-report.md`，记录完整的 A→F 过程、测试数、commit 数、关键决策
2. **PROJECT-OVERVIEW.md 同步** — 更新版本路线图、当前阶段、版本历史表
3. **规则审计** — 检查本次循环中产生的新规则是否已写入文档，对话中的规则不算规则
4. **下一版本种子** — 列出候选功能池，供下一轮 C 阶段 brainstorming 使用

### 阶段 T: 系统测试（强制门禁）

**这是整个循环的质量闸门。T 不过，不准进 E。**

| # | 检查项 | 执行方式 | 说明 |
|---|--------|---------|------|
| T1 | 全量测试 | `pytest tests/ -v` | 必须 100% 通过 |
| T2 | 回归检查 | 对比上一版本测试数 | 只增不减，确认无测试被删除 |
| T3 | 边界条件 | 子代理专项检查 | 空输入、超长输入、并发、超时、DB锁 |
| T4 | 集成烟雾 | 子代理 | 启动服务器 → 所有路由 200 → 模板正常 |
| T5 | 性能检查 | 子代理 | N+1查询、大循环、未关闭连接、多余commit |
| T6 | 安全回归 | 子代理 | XSS、SQL注入、SSRF、密钥泄露快速扫描 |
| T7 | 覆盖率 | `pytest --cov` | 对比上一版本，目标持续提升 |
| T8 | 问题修复 | 子代理 | T1-T7 发现的所有问题修复 |

**T 阶段输出:** 测试报告 + 发现问题清单 + 修复记录 → 写入 `docs/superpowers/reports/YYYY-MM-DD-cycle-N-report.md`

### Bug Hunting 机制（v1.0 起）

四个专项 Hunter 作为 **B 阶段和 T 阶段的固定执行模块**，在审计和测试中执行自动化缺陷搜捕。

| Hunter | 执行时机 | 扫描范围 | 职责 |
|--------|---------|---------|------|
| 边界猎人 | B, T | B: 全量 / T: 增量 | 空输入、超长输入、并发、超时、DB 锁 |
| 体验猎人 | B, T | B: 全量 / T: 增量 | UI 死链接、错误文案、加载态缺失、空态处理 |
| 安全猎人 | B, T | B: 全量 / T: 增量 | SQL 注入、XSS、密钥泄露、路径遍历 |
| 正确性猎人 | B, T | B: 全量 / T: 增量 | 逻辑矛盾、数据不一致、遗漏的错误处理 |

**阶段 B 扩展结构：**
1. B1: 架构+安全+质量+性能审计（现有）
2. B2: 四 Hunter 全量扫描（新增）
3. B3: 修复 + 规则审计（现有）

**阶段 T 扩展结构：**
- T3: 边界猎人 增量扫描（替代原手工边界检查）
- T6: 安全猎人 增量扫描（替代原手工安全扫描）
- 其他 T 检查项不变

**学习回路：** 每个 cycle 的猎杀报告末尾增加"建议强化规则"条目。若连续两个 cycle 的同一 hunter 发现同类问题，该建议自动升级为 PROJECT-OVERVIEW.md 铁律（R11+）。

**空结果协议：** 若某 hunter 零发现，触发验证：确认 hunter 运行了 + 扫描了正确文件集。验证通过记录 "clean"，不视为异常。

### 阶段 D 内部流程

```
每个 task:
  实现子代理 → spec审查 → 代码质量审查 → ✅ → 下一个
```

### 审查视角

| 视角 | 关注点 | 谁负责 |
|------|--------|--------|
| **架构师** | 模块边界清晰、接口设计合理、技术选型正确、扩展性 | spec 合规审查 |
| **工程师** | 代码质量、错误处理、边界条件、测试覆盖、性能 | 代码质量审查 |
| **PM** | 范围控制、优先级、里程碑、风险、依赖 | 主会话协调 |
| **QA** | 测试策略、验收标准、回归风险 | 代码质量审查 |
| **安全** | 数据保护、输入验证、最小权限 | 代码质量审查 |

## 九、开发铁律（2026-06-09 回顾总结）

从 8 个版本（v0.1→v0.8）的开发中提炼出的强制性规则。每一条都来自实际踩过的坑。

### 会话恢复

**R1: 恢复先验收。** 新会话恢复时，第一步是读 PROJECT-OVERVIEW 了解规则，第二步是阶段 A（验收上一版本）。没有 Phase A 不得进入开发。即使 Cycle Report 存在，仍需验证测试数、commit 数、覆盖率与 report 一致。

**R2: 用 PROJECT-OVERVIEW 而不是 Report 恢复。** Report 只说当前版本做了什么。PROJECT-OVERVIEW 包含完整的循环框架、规则、约束。恢复时应读两者，但 PROJECT-OVERVIEW 优先。

### 实现约束

**R3: htmx endpoint 返回 HTML，不是 JSON。** 任何被 `hx-get`/`hx-post`/`hx-trigger` 消费的 endpoint，必须返回 `HTMLResponse`，不是 `JSONResponse`。JSON 在浏览器里显示为乱码。此规则来自 v0.7 两次同样的 bug（concept extraction + recommendations）。

**R4: 替换函数前 grep 所有调用方。** 修改一个被多处调用的函数的签名、行为、或存在性之前，必须 `grep` 整个代码库找到所有引用。替换后 grep 确认旧函数名已无引用。v0.7 的 `get_recommendations_gap → get_recommendations_cluster` 差点漏了 weekly review 里的调用。

### 修复与审计

**R5: "修了"必须明确是什么修了。** plan 修复（改 .md 文件）≠ code 修复（改 .py 文件）。审计发现的问题在讨论结束后，必须逐项确认是 plan fix 还是 code fix。code fix 必须有对应的 commit。

**R6: code review 包含同 cycle 前序 task 的交叉校验。** 检查新代码是否复用了本 cycle 前面 task 刚提取的 helper/函数。v0.8 scheduler 重复了 `_build_nodes_and_edges` 就是漏了交叉校验。

### 审查门禁

**R7: task 间的审查不可跳过。** subagent-driven 流程中，spec review + code quality review 必须在下一个 task 开始前完成。发现的问题必须在同一 task 内修复。不得攒到 Phase T 一起修。

**R8: 发现的问题要么修，要么不修——不能"文档化"。** 加一条注释说明"这里是故意的"不是修复。如果问题不值得修，在 cycle report 的"已知问题"中明确记录。如果值得修，修掉。

### 流程顺序

**R9: 先 scoping 再工具。** 在需求范围确定之前，不讨论可视化面板、技术选型、具体实现。先定"做什么"，再定"怎么做"，最后才到"用什么工具"。

**R10: Phase T 是强制门禁，不是可选项。** 任何版本在阶段 D 完成后，必须执行完整的 T1-T8。T 不过，不准进 E。v0.6 恢复时跳过了 Phase T 直接开发，导致 25 个边界/性能/安全问题在后续才被发现。

**R11: Bug Hunting 学习回路。** 每个 cycle 的 Hunter 报告末尾必须包含"建议强化规则"。若同一 Hunter 连续两个 cycle 发现同类问题，该建议自动升级为铁律。Hunter 零发现时必须触发验证步骤确认 Hunter 确实运行了。
